# ADR-0014: MatchupContext PFF grade population — trailing season-to-date, not a per-week snapshot

**Status:** Accepted (draft spec), pending Model Analytics Expert confirmation; direction for Data Integration Engineer's next PFF ingestion pass
**Date:** 2026-09-13
**Owner:** Architect
**Related:** PRD Section 6 (`MatchupContext` — Run game, Pass protection, Coverage rows), ADR-0003 (cross-sectional/trailing population pattern for `GameEnvironmentScore`), ADR-0011 (shared shrinkage form), Data Integration Engineer's live PFF ingestion test (0/210 matches on a live pre-kickoff DK slate)

## Context

The Data Integration Engineer's live ingestion test against today's DK slate returned 0/210 player matches on PFF's facet grade endpoints and flagged an open question: PFF's facet endpoints (`/v1/facet/offense/run_blocking`, `/v1/facet/offense/pass_blocking`, `/v1/facet/defense/run`, `/v1/facet/defense/coverage_scheme` — the four endpoints `MatchupContext`'s Run game, Pass protection, and Coverage rows all depend on) are post-game stat/grade summaries, computed from film after plays happen. For a slate whose games haven't kicked off, "this week's" grade doesn't exist yet — there's nothing to return.

Chris confirmed this is expected, not a data-source mistake to route around: *"for PFF, this gives us historical performance — not meant to be a predictive grade for this game."* PFF grades are inherently trailing by construction. The correct usage is the same pattern already established for `GameEnvironmentScore`'s pace/PROE in ADR-0003: season-to-date-through-last-completed-week trailing data, used predictively for the upcoming week's matchup — not a same-week snapshot that structurally cannot exist before kickoff.

This ADR makes that population explicit for `MatchupContext`'s PFF-grade inputs (it was previously left implicit/ambiguous in Section 6's text) and specifies exactly how "trailing" is computed, since that's a real design decision, not automatically "whatever's easiest."

## Live API check: does the general facet family support a week-list the way the signature family does?

Phase 0 noted the `signature` endpoint family's `week` parameter accepts a comma-separated list. Checked live, against the actual OpenAPI spec (`https://developer.pff.com/openapi.json`, same source already used to confirm the API key and endpoint shapes), whether the general `facet` endpoints `MatchupContext` depends on support the same thing — not assumed to be signature-family-only.

**Confirmed: yes, identically.** All four endpoints (`offense/run_blocking`, `offense/pass_blocking`, `defense/run`, `defense/coverage_scheme`) reference the exact same shared `week` parameter component as every other facet/signature endpoint. Its description, verbatim: *"Week filter. Never coerced except by `ref-games`, so a comma-separated list is accepted such as `1,2,3`... On exports, a value spanning too many weeks is rejected with a `422`."* That export-only cap doesn't apply to the default JSON response path this project uses.

**A second finding, better than what was asked:** the response shape confirms PFF **server-side aggregates** across the requested week list — it is not one row per player per week that the caller has to merge. Checked directly against the response schema and live examples: each row carries a `player_game_count` field (the number of games within the requested week range that player actually appears in) and grade/snap-count fields with no `week` column at all — i.e., requesting `week=1,2,3` for a player who played all three returns **one row** with `grades_run_block` etc. already computed across that span, not three rows to aggregate client-side. This resolves the open question more favorably than either of its two framed outcomes ("supports lists" vs. "pull each week individually and aggregate client-side") — **it's a single call, and PFF does the aggregation.**

## Decision

### 1. Population: season-to-date cumulative through the most recently completed week, via one API call

`MatchupContext`'s PFF-grade inputs (run-block/run-defense, pass-block/pass-rush, coverage man/zone) use **season-to-date cumulative grades**, pulled with `week=1,2,...,W-1` (every completed week so far this season, generated programmatically — no range/dash shorthand exists, so the Data Integration Engineer's ingestion code builds the comma-separated list itself) against the same four facet endpoints already in use, rather than a single most-recent-week value or a fixed rolling window (e.g., trailing 3–6 weeks).

**Why cumulative over a fixed rolling window:** PFF grades for an individual lineman or defender in a single week are drawn from a small, noisy snap sample (the example payloads above show single-week snap counts in the 15–70 range) — the same small-sample-noise problem ADR-0003 already reasoned through for pace/PROE, and the same reason ADR-0006 required a snap-count floor before trusting an individually-identified defender's grade. A season-to-date cumulative grade averages over more snaps as the season progresses, reducing that noise, and PFF's own server-side aggregation already applies PFF's standard (presumably snap-weighted) grading methodology across the requested span rather than this project reinventing an averaging scheme. A fixed rolling window (e.g., trailing 6 weeks) would reintroduce a version of the same noise problem in early-to-mid season and adds an arbitrary window-length parameter with no clear advantage over cumulative for this data shape.

### 2. No reuse of ADR-0011's `n/(n+k)` shrinkage-toward-prior-season-baseline — different statistical shape, explicit reasoning

Considered directly, per the instruction not to assume automatically: should these trailing grades blend toward a prior-season baseline the same way pace/PROE do (ADR-0003/ADR-0011)? **No, not for v1**, and the reasoning is specific, not just "different for its own sake":

- Pace/PROE are **team-level** rate stats where the referent (the team, its coaching staff, its scheme identity) is reasonably stable across a season and even across seasons — that's exactly why blending a team's thin current-season sample toward *that same team's* prior-season number is defensible.
- PFF grades are **individual-player** performance measures. The equivalent, statistically correct shrinkage anchor would be *that specific player's own* prior-season grade — not "the team's" prior-season grade at that position, which would repeat the exact identity-mismatch bug already found and fixed twice this project (ADR-0009's QB-continuity fix, ADR-0012's returner-identity fix): offensive lines and defensive personnel turn over meaningfully year to year, so blending a current right tackle's thin sample toward whoever played right tackle for that team last year would frequently reference a different person's performance.
- Building a fully general, identity-matched, player-level shrinkage system for every offensive lineman and defender `MatchupContext` touches (potentially dozens of players per team) is a materially larger scope addition than what this round calls for — a "small, precise clarification," per the brief, not a new formula. It's flagged below as a v1.1 candidate reusing the identity-matching pattern already proven out in ADR-0009/ADR-0012, not invented fresh here.

**What v1 does instead — a narrow, explicit fallback for the one case that's actually degenerate, not a general early-season smoothing mechanism:** in week 1, there are zero completed weeks of current-season data — cumulative-through-last-completed-week is undefined, not just noisy. For that specific case only: fall back to that **same player's** own prior-season (2024 and/or 2025) PFF grade, matched by PFF's own stable `player_id` (confirmed as a real, persistent per-player identifier in ADR-0013's crosswalk check) — a legitimate same-identity reference, not the team-level mistake described above. If no prior-season PFF record exists for that player (a rookie, or a player who didn't qualify for grading), fall back further to a league-average-by-position grade for that stat. From week 2 onward, the current-season cumulative population (section 1) is used directly with no blending, and the early-season noise this leaves unaddressed (a week-2 grade still reflects only 1–2 games) is accepted as a known v1 limitation rather than smoothed — `MatchupContext`'s existing 0.85x–1.15x capped-multiplier structure already bounds how much a single noisy early-season grade can move a projection, which is a real, if partial, mitigation already in place.

### 3. Direction for the Data Integration Engineer's next PFF ingestion pass

Replace `pff.py`'s single-week facet query (`week=<current_week>`) with a season-to-date query for each of the four endpoints above: `week=1,2,...,W-1` where `W` is the current week, built as a comma-separated string client-side (confirmed live: no range/dash syntax exists, only explicit lists). This is **one API call per endpoint** (not one call per completed week merged client-side) — PFF's own server-side aggregation, confirmed above, does the combining. For week 1 specifically, skip the current-season call entirely (it would return an empty/undefined result — zero completed weeks) and instead pull the same endpoints with `season=2024,2025` (using the already-confirmed `season_list` comma-separated form) to get prior-season grades for the fallback in section 2, matched by `player_id`. The response's `player_game_count` field is a free, already-provided per-player sample-size indicator — worth surfacing in ingestion output/logs for QA spot-checks, even though it isn't a formal gate the way ADR-0006's snap-count floor is for the coverage-alignment approximation specifically.

## Alternatives considered

- **Single most-recent-completed-week snapshot** (the ambiguous default the 0/210 test exposed as broken pre-kickoff, and noisy even when a completed week exists). Rejected — see small-sample-noise reasoning above.
- **Fixed rolling window (e.g., trailing 3–6 weeks)**, mirroring how a reader might expect "recent form" to be computed. Rejected as the primary population — see section 1 rationale; it doesn't have a clear statistical advantage over cumulative for this data shape and adds an arbitrary window-length parameter. Not ruled out permanently: if backtesting later shows grades meaningfully decay in predictive value beyond some window (a real possibility for, e.g., a player returning from injury or a scheme change), a rolling window could be revisited — that's a Model Analytics Expert backtesting question, not decided here.
- **Full `n/(n+k)` player-level shrinkage toward prior-season baseline, applied every week, not just week 1.** Rejected for v1 scope reasons — see section 2. Flagged as a v1.1 candidate.
- **Pull each completed week individually and aggregate client-side.** Rejected once the live check showed PFF already does this server-side — building client-side aggregation would be redundant work reproducing what a single correctly-formed API call already returns.

## Consequences

- PRD Section 6's `MatchupContext` table needs its PFF-grade population stated explicitly as "trailing, season-to-date through the most recently completed week" for the Run game, Pass protection, and Coverage (man/zone piece) rows — previously ambiguous, now matching the language already used for `GameEnvironmentScore`'s pace/PROE.
- `pff.py` (Data Integration Engineer implementation, not touched by this ADR) needs its query construction updated per section 3 — a real but small change: build a week-list string instead of a single week value, and add the week-1 prior-season fallback path.
- The week-1 prior-season fallback needs the same `player_id` crosswalk already established in ADR-0013 — no new mapping layer, reuses existing work.
- Full player-level shrinkage (beyond the narrow week-1 fallback) is explicitly deferred, not decided against permanently — a v1.1 candidate for the Model Analytics Expert to evaluate once season-long data exists to check whether early/mid-season grade noise is actually hurting `MatchupContext`'s multiplier accuracy enough to justify the added complexity.
