## 1. Purpose

Build a lineup construction tool for DraftKings NFL Classic GPP contests. The tool blends external projection and grading sources with an in-house game-environment and correlation model, then generates a small slate of lineups built around explicit stacking theses rather than raw point-per-dollar optimization.

The technical pipeline (Section 5) is a single linear system in v1, not the eight-agent runtime the MLB optimizer uses — that stays a later-phase option, not a v1 requirement. Separately, the *work* of building, validating, and running that pipeline is owned by a defined team of Claude Code subagents (Section 10). Those are two different things: one is the shape of the software, the other is who's responsible for what while it gets built and operated.

## 2. Scope & Contest Focus

- **Format:** DraftKings Classic NFL slate, GPP only. Cash games are explicitly out of scope for v1 — no floor-optimized or high-ownership "safe" mode.
- **Weekly contest mix:** Chris builds 3 lineups per slate and enters them across a spread of contests — a single-entry contest, a handful of 3-max, 5-max, and 20-max entry contests, and all three lineups into the Millionaire Maker (150-max entries per user, massive overall field). The same 3-lineup set has to hold up across that whole range, from small-field contests where the optimal build looks close to the chalk play, to a field the size of the Millionaire Maker where leverage and differentiation matter far more. Lineup construction (Section 7) and output (Section 8) are built around this 3-lineup set, not a larger N-lineup batch.
- **Slate types:** Main slate (Sunday 1pm window) is primary. Showdown/Captain Mode slates are out of scope for v1; the roster and correlation logic differ enough to warrant a separate build later.
- **Cadence:** Weekly, in-season. The tool needs to run a full cycle — data pull through lineup output — inside a single afternoon before lock.

## 3. Roster & Contest Mechanics

DK Classic NFL roster: QB, RB, RB, WR, WR, WR, TE, FLEX (RB/WR/TE), DST. $50,000 salary cap, nine roster spots.

Relevant mechanics the model needs to respect:
- No hard rule against RB or WR facing the opposing DST in the same lineup, but the correlation model should price that matchup as negative.
- DST scoring is volatile and swings on defensive/special teams touchdowns and sacks — treat it as a separate projection problem from offensive skill positions, not a scaled-down version of the same model.
- Late swap is available on DK; the tool should flag players in early games separately from those in the late/Sunday-night window so Chris can hold flexible spots where it makes sense.

## 5. System Architecture (v1)

A single linear pipeline, in this order:

1. **Ingestion** — pull salaries/slate info from DraftKings, projections and grades from PFF, RotoGrinders, and Footballguys, historical stats from nflverse, lines from the odds API, and weather where relevant. *Phase 0 note:* PFF and RotoGrinders both return clean JSON; Footballguys' authenticated projections endpoint returns server-rendered HTML (`<table>` fragments), so its ingestion step needs an HTML table parse (e.g. `pandas.read_html` or a targeted `tr[data-playerid]` scrape), not a JSON decode — a real per-source branch in this step, not a detail to handle later. The nflverse "foundation layer" pulls from `import_pbp_data()` (current) rather than `import_weekly_data()` (stale, no current season) — target share, red-zone share, and aDOT are computed by aggregating play-by-play ourselves rather than pulled pre-aggregated.
2. **Normalization** — reconcile player IDs across sources (DK's naming doesn't match PFF's or Footballguys' cleanly), resolve name collisions, flag players missing from any source. **Design resolved (ADR-0013, `docs/adr/0013-player-id-reconciliation.md`):** checked live whether the nflverse/ffverse ID crosswalk (`nfl_data_py.import_ids()`) already solves this — it partially does. It directly covers **PFF** (`pff_id`, verified live against PFF's own API) and nflverse's own `gsis_id` (used as the canonical internal player ID, since the foundation layer is already keyed on it). It does **not** cover **DraftKings** or **RotoGrinders** at all (no such ID columns exist), and its **Footballguys**-shaped `pfr_id` field is unreliable as a join key — a live check found Footballguys' `data-playerid="GibbJa00"` for Jahmyr Gibbs does not match the crosswalk's real `pfr_id` for Gibbs (`GibbJa01`); `GibbJa00` belongs to a different real player (Jack Gibbens). DK, RotoGrinders, and (despite appearances) Footballguys therefore all go through the same fallback matcher: normalized name + normalized team + normalized position, gated behind a mandatory name-verification check even on the PFF crosswalk path. Ambiguous matches and genuine name collisions are never auto-resolved — they're flagged for QA rather than silently guessed. Two more per-source normalization needs surfaced live and are handled by small alias tables: PFF labels running backs `"HB"` where the rest of the pipeline uses `"RB"`, and team abbreviations differ across sources (e.g., DK's `LV`/`GB`/`WAS` vs. the crosswalk's `LVR`/`GBP`/`WAS`). Full design, live findings, and the outcome policy for no-match/ambiguous/collision cases in ADR-0013; output shape (`PlayerIdentity`) scaffolded in `src/nfl_dfs/normalization/identity.py`.
3. **Projection blending** — combine vendor projections with the in-house model built on nflverse data into a single blended projection per player, with a defensible weighting rationale rather than an arbitrary average.
4. **Matchup adjustment** — apply `MatchupContext` (Section 6) to the blended projection, so trench and coverage matchups shape the number rather than sitting next to it as a footnote.
5. **Game environment scoring** — compute `GameEnvironmentScore` per game (Section 6).
6. **Correlation/stack scoring** — compute `StackProfile` per team/game combination (Section 6).
7. **Ownership/leverage layer** — use RotoGrinders ownership projections to flag high-owned chalk and identify leverage spots (strong player, low projected ownership). *Not yet built.* **Data note (ADR-0023):** RotoGrinders ResultsDB (Section 4) now gives this stage a confirmed source of real, *settled* field ownership (by finisher tier) for the same DK contest types Chris enters, going back to the 2020 season — a candidate ground truth for checking whether LineupHQ's *projected* ownership tracks real field behavior, not just a projection with nothing to validate it against. The actual leverage-layer design is still future Architect scope, not resolved by that ADR.
8. **Lineup construction** — an ILP-based optimizer, constrained by salary cap, roster rules, and the stack theses defined in Section 7, producing a small set of distinct lineups rather than N near-duplicates.
9. **Output** — lineup list plus an exposure report showing how often each player appears across the generated set.

Simulation (Monte Carlo outcome modeling, the way the MLB build uses it) is deferred to v2. For v1, `GameEnvironmentScore` and `StackProfile` carry the correlation logic instead of full game simulation.

## 6. Core Analytical Components

**Status legend (post-Phase 0):** Phase 0 (`docs/phase0/data-availability.md`) confirmed the data granularity behind every input below. "Data-confirmed" means the specific field/endpoint exists and returns real values at the assumed granularity — it does **not** mean the formula is implemented. Per the Architect ground rules, a formula only moves from draft to implemented once both the Model Analytics Expert (statistical rigor) and the Fantasy Football Expert (football validity) sign off. Nothing in this section has that sign-off yet — treat every row as **data-confirmed, pending MAE + FFE review**.

### GameEnvironmentScore
**Status: all four scored components are data-confirmed; weights renormalized to sum to 100 and z-score population/window now fully specified (ADR-0003); weather-impact sub-component reshaped post-Phase-0 to add a temperature curve and a piecewise wind curve, then magnitude-damped to 60% of cited research figures with a distinct "external, unvalidated" confidence tag (ADR-0002, ADR-0007). Still unvalidated: whether these weights survive the ADR-0003 correlation-check prerequisite below.**

A per-game score, 0–100, computed as a weighted composite. **Weighting note (ADR-0003):** the four scored components below are renormalized to sum to 100 — the prior 40/20/20/10 draft summed to only 90 once the non-numeric injury/role flag was correctly excluded from the numeric total; each weight here is the prior draft weight ÷ 0.9. The injury/role flag remains outside the 100-point scale entirely (see below), not folded in at a reduced weight.

- **Implied team total (44.4%)** — derived from spread and game total. *Z-score population and window (ADR-0003):* cross-sectional per week — each team's current-week implied total is z-scored against all 32 teams' implied totals for that same week, not pooled across the season, so the score answers "unusual this week" rather than blending in earlier-season scoring/rule drift. No early-season fallback is needed for this component — a full 32-team Vegas line exists from week 1 onward. **Population clarified by live testing (ADR-0016, `docs/adr/0016-odds-api-missing-inplay-fallback.md`):** a live pull found only 28/32 teams — the Odds API drops markets entirely for games already in progress at pull time rather than returning a stale line. "All 32 teams" now means each team's most recently available *pre-kickoff* line: live if that team's game hasn't started at pull time, else the most recently cached pre-kickoff value from an earlier pull that week (ingestion must run at least daily through the week, not just once before lock, to keep that cache fresh); if no cached value exists at all for a team, its implied-total input is flagged unavailable rather than imputed. *Data-confirmed:* the Odds API (`the-odds-api.com`) returns per-bookmaker spreads and totals including DraftKings' own line specifically — the line to track since it's the book whose pricing the correlation model should follow most closely.
- **Pace (22.2%)** — offense's situation-neutral plays-per-game. *Z-score population and window (ADR-0003):* cross-sectional per week (all 32 teams, as-of the current week, using only completed weeks 1..W-1 — never the current week's own in-progress data). *Early-season fallback:* blend each team's current-season-to-date value with that team's 2024/2025 prior-season baseline using the shared empirical-Bayes shrinkage form (ADR-0011): `w = weeks_played / (weeks_played + 6)` — asymptotic, not a capped ramp; even a full 17-week season still carries ~26% weight on the prior-season baseline, which is a deliberate, more conservative posture than an earlier draft's capped linear version (see ADR-0011 for the comparison). *Data-confirmed, with a build note:* `nfl_data_py`'s `import_weekly_data()` convenience function is stale (its underlying release only covers through the 2024 season); pace has to be derived by aggregating `import_pbp_data()` play-by-play ourselves instead of pulling a pre-aggregated stat. See Section 5 note.
- **Pass rate over expectation, PROE (22.2%)** — league-standard PROE metric. Same z-score population/window and early-season shrinkage-blend fallback as pace above (ADR-0003). *Data-confirmed*, same `import_pbp_data()` aggregation path as pace.
- **Weather impact (11.1%, outdoor games only; redistributed to the other three for indoor/dome games)** — a penalty function on wind speed, temperature, and precipitation. *Data source: data-confirmed*, source changed from the PRD's original placeholder — no paid "Weather API" is needed — Open-Meteo (free, keyless, primary) plus NWS/`api.weather.gov` (free, keyless, US-only secondary cross-check, needed because Open-Meteo's global GFS/ECMWF model under-reads thunderstorm probability relative to NWS's regional HRRR/RAP models) cover this, matching the MLB build's approach. Section 4's "Weather API" row is superseded by this. Re-confirmed directly (not just carried over from Phase 0) that Open-Meteo's hourly `temperature_2m` field returns real values alongside `wind_speed_10m` and `precipitation` — a live test pull (`GET https://api.open-meteo.com/v1/forecast?...&hourly=temperature_2m,wind_speed_10m,precipitation`) returned populated `temperature_2m` values in °F, so the sub-component below has a confirmed data source, not just an assumed one.

  **Curve calibration: external, unvalidated — sourced from public research, not this project's backtested data (ADR-0007).** This is a distinct, weaker confidence level than the "data-confirmed" tag above — data-confirmed means the wind/temperature/precipitation *input fields* are real and pulled; it says nothing about whether the *curve shape and magnitude* applied to those fields is correctly calibrated. Every other Section 6 formula at least uses this project's own data distributions (this season's grades, this week's lines) even before weight validation; the weather curve below is fit to nothing but external research, so per ADR-0007 the cited effect sizes are applied at **60% of stated magnitude** for v1 — a specific, conservative damping (not the full 50–75% range's midpoint or floor) chosen because multiple independent sources converge on similar effect direction and rough magnitude (arguing against maximum damping) while none were fit against DK scoring specifically and one source dates to a meaningfully less pass-friendly era (arguing against applying the figures at anything close to full strength).

  - **Wind** — reshaped from a flat "above 15mph" cutoff to a piecewise curve, since the penalty accelerates rather than stepping once: negligible below ~10mph; mild 10–15mph; moderate 15–20mph; steep above 20mph. Cited research (ADR-0002) puts QB ANY/A at ~5.79 below 10mph vs. ~4.62 at 20mph+, and field-goal conversion falling ~6% at 20mph+ even though average attempt distance also shortens ~7 yards in that wind. **Damped to 60% for v1 (ADR-0007):** effective ANY/A target ~5.09 at 20mph+ (~12% relative drop, not ~20%); effective FG-conversion drop ~3.6%, not ~6%. **10–20mph interior shape specified in ADR-0015** (`docs/adr/0015-weather-subcomponent-completion.md`): a three-point piecewise-linear curve — (10mph, 5.79), a derived 15mph midpoint (5.365, from ADR-0002's own stated "15→20mph step is ~1.5–2x steeper than 10→15mph" ratio), (20mph, 4.62) — replacing an unreviewed quadratic interpolation an earlier ingestion pass had implemented as its own engineering judgment call; same three-point construction applies to the FG-conversion curve (15mph midpoint ≈ −2.18%, pre-damping).
  - **Temperature** — new sub-component; Section 6 previously had no temperature input at all. U-shaped curve, open-air games only: neutral 55–85°F (no meaningful passing effect); cited ~5% passing-production dip 25–55°F, cited ~8% decrease below 25°F or above 85°F — cold and heat converge to roughly the same penalty at the extremes, so heat is a real, symmetric effect on passing offense, not only a cold-weather phenomenon. **Damped to 60% for v1 (ADR-0007):** ~3% dip in the 25–55°F band, ~4.8% (~5%) decrease below 25°F or above 85°F. Separately, heat also degrades grip/ball security (more of a fumble/accuracy risk than a scoring-rate one) and RBs specifically underperform in heat more than other positions — **not** folded into this team-agnostic game-level score for v1; see the dome/outdoor travel note below.
  - **Precipitation — magnitude specified in ADR-0015** (`docs/adr/0015-weather-subcomponent-completion.md`), closing a real gap: this sub-component previously had no quantified magnitude at all, just a binary "any measurable precipitation reduces the score." Rain and snow are treated separately — different mechanisms (rain: grip/accuracy; snow: additionally footing, visibility, ball security) with different cited magnitudes, not a shared curve. Intensity bands use standard meteorological rate thresholds (rain: light <0.10in/hr, moderate 0.10–0.30in/hr, heavy >0.30in/hr; snow: light <1in/hr, moderate 1–2in/hr, heavy >2in/hr), classified from Open-Meteo's `rain`/`snowfall` fields — confirmed live to be distinct from the combined `precipitation` field, no new data dependency. Effect magnitude is expressed as a completion-percentage-point (pp) drop:

    | Band | Full-strength | Damped (60%, ADR-0007 convention) |
    |---|---|---|
    | Light rain | −2.3pp (PFF, cited) | −1.4pp |
    | Moderate rain | −3.4pp (PFF, cited) | −2.0pp |
    | Heavy rain | −5.0pp (Architect-extrapolated — no source gives a heavy-rain figure directly) | −3.0pp |
    | Light snow | −3pp (Architect-extrapolated) | −1.8pp |
    | Moderate snow | −7pp (The Fantasy Footballers, cited — used as the intensity-undifferentiated average's moderate anchor) | −4.2pp |
    | Heavy snow | −12pp (Architect-extrapolated) | −7.2pp |

    Extrapolated bands are flagged as such, not presented at the same confidence as the two directly-cited bands — same discipline as the QB-continuity and returner-cold-start fixes elsewhere in this PRD (no invented figure passed off as sourced). Secondary effects documented but not folded into the score, same treatment as heat's grip/RB note above: PFF's rain data shows fumbles-per-carry rising sharply and non-linearly with intensity (+0.003/carry light, +0.015/carry moderate — a 5x jump) and drop rates rising 1–6% in precipitation generally — flagged as a candidate `MatchupContext`-level (receiver/RB-specific) adjustment for the Fantasy Football Expert, not decided here.

  **Combining wind, temperature, and precipitation into one weather sub-score (ADR-0015):** previously unspecified — Section 6 describes weather as one 11.1%-weighted sub-component, but wind/temperature/precipitation were each written up independently with no combination rule, which meant precipitation's magnitude alone still couldn't produce an actual score contribution. Each sub-effect is converted to a relative passing-efficiency degradation fraction (wind and precipitation via a stated baseline — 5.79 ANY/A, 64% completion rate respectively; temperature is already expressed as a %), then combined via the same capped log-space method used throughout Section 6 (ADR-0005/0009/0012 precedent): sum the log-multipliers, cap the combined deviation at **±30%** (matching `DSTProjection`'s three-factor cap, ADR-0009 — three distinct physical mechanisms, not a shared confound, so wider than the two-factor ±20%). `weather_subscore = 11.1 × exp(clip(Σ ln(m_i), ln(0.70), ln(1.30)))`.

  **Retractable-roof and SoFi Stadium classification — confirmed v1 policy (ADR-0015):** retractable-roof stadiums default to closed/dome for the automated weekly pull (no live roof-status feed exists); SoFi Stadium (open-sided, fixed translucent-canopy design) is classified as a dome for weather short-circuit purposes, since the right criterion is functional (does weather reach the field) not architectural. Both were already-implemented engineering defaults, now promoted to reviewed spec rather than left as code-comment-only judgment calls.

  **Known v1.1 candidate, reprioritized this pass — dome-to-cold-outdoor travel (ADR-0007 context, Fantasy Football Expert item 4):** the curve above applies identically to both teams in a game regardless of home stadium type, but a dome team traveling to a cold, windy outdoor game is a materially worse spot than the home team built for that environment — one of the more well-established fade signals in DFS, using data (stadium type: dome vs. outdoor) that's already available with no new dependency. This was previously logged as a vague "candidate future `MatchupContext` adjustment"; it's now flagged explicitly as **next in line for v1.1**, not a someday/maybe item. Whether to pull it forward into v1 itself is a scope call for the Product Owner and Chris, not one the Architect is resolving unilaterally here — see Section 11.

  All thresholds above (wind tiers, temperature bands, the specific ANY/A and FG-conversion figures, and the 60% damping factor) are draft numbers — the band edges and un-damped figures pulled from public research and cited in ADR-0002, the damping factor decided in ADR-0007 — not yet validated against this project's own backtested data. Same status as the rest of Section 6: data-confirmed input, pending Model Analytics Expert sign-off before the exact curve shape and damping factor are finalized.
- **Injury/role uncertainty (flag, not a score — outside the 100-point scale)** — this one doesn't blend into the composite numerically; it's a confidence flag attached to the score (e.g., "moderate," "high uncertainty") when a starter's status is unresolved close to lock. No dedicated Phase 0 data check was needed here — this depends on ingestion timing/freshness (DK, PFF, RotoGrinders, Footballguys role notes) rather than a new source. **Source and rollup policy confirmed (ADR-0017, `docs/adr/0017-game-environment-score-computation-policy.md`):** wired to RotoGrinders' "Situation Room" injury report (per-player `STATUS` code plus a graded 0–10 `IMPACTRTG` severity score). A confirmed "Out" status is resolved information, not uncertainty (a player-pool-exclusion concern downstream, not this flag's job); any other status is unresolved and contributes, graded off the *worst* unresolved player's `IMPACTRTG` on that team: below 2 → no flag (negligible-impact players don't dilute the signal), 2–4 → "moderate", 5+ → "high_uncertainty". Thresholds are stated v1 starting points on RotoGrinders' own scale, not backtested — same status as every other Section 6 constant sourced this way.

**Two additional computation-policy decisions, confirmed in ADR-0017:**
- **Z-score → points mapping:** each z-scored component (implied total, pace, PROE) maps to points via the standard normal CDF — `points = weight_pct × Φ(z)` — rather than a linear clip to a fixed bound, so z=0 lands at exactly half that component's weight with no arbitrary saturation constant.
- **Missing implied total:** if a team has no live Odds API line and no cached pre-kickoff fallback exists either (ADR-0016 tier 3), the *entire* composite is marked unavailable rather than redistributing implied total's 44.4% weight the way a dome redistributes weather's 11.1% — a missing implied total signals a real pipeline failure, unlike a dome's known/benign/structural absence, and silently reweighting around it would let a materially degraded, pace/PROE-dominated score look shape-identical to a normal one to downstream consumers, particularly `StackProfile`'s `min()` bottleneck logic. Downstream construction should treat such a team-week as excluded from that week's stack-thesis consideration, not zeroed out or imputed.

Output: a 0–100 score per team per game, plus the uncertainty flag. Weights above remain a starting proposal for Architect and Model Analytics Expert to validate against a season or more of backtested data — Phase 0 confirmed the *inputs* exist, not that 44.4/22.2/22.2/11.1 is correct; that validation is explicitly deferred to backtesting per the original spec, not a Phase 0 blocker.

**Backtesting prerequisite before these weights are locked (ADR-0003):** a Vegas total already prices in a team's expected play volume and pass rate, so implied total (44.4%) and pace+PROE (44.4% combined) risk rewarding the same underlying "high-volume passing environment" signal more than once. Before the weights above are treated as final, correlate season-to-date implied-total z-score against pace z-score, and against PROE z-score, across all team-weeks in the backtest window. Action threshold: `|r| > 0.3–0.4`. If exceeded: either residualize pace/PROE against implied total before z-scoring, or collapse pace+PROE into a single "play-volume" factor and re-derive a two-factor weighting. If not exceeded, the three-way split stands as specified.

### StackProfile
**Status: game-stack viability now has an actual formula (ADR-0004) — bottleneck (`min`) logic across both teams' `GameEnvironmentScore`, with a spread-magnitude dampener on the bring-back thesis specifically. Depends on `GameEnvironmentScore`, now renormalized to a clean 0–100 scale (ADR-0003), and on `MatchupContext`. New this pass (ADR-0019): `RoleShare` + `BlowoutVolumeDiscount` — a player-level game-script usage-share signal, empirically researched against 2023–2025 nflverse data rather than assumed, and deliberately narrower in scope than Chris's original framing once the data came back (see below). This also closes `primary_stack_candidates`/`bring_back_candidates`' standing data blocker — see `RoleShare`. Latest pass (ADR-0021): `bring_back_candidates` is now gated on `game_stack_viability` itself, not populated unconditionally — see below.**

Defines the correlation thesis for a given team/game:
- Primary stack candidates (QB + top 1–2 pass-catchers), ranked by `RoleShare` (below) and `MatchupContext` favorability, not raw season totals alone. **Data gap now closed (ADR-0019):** `src/nfl_dfs/correlation/stack_profile.py`'s `primary_stack_candidates`/`bring_back_candidates` fields have been `None` pending nflverse play-by-play aggregation to the player level — `RoleShare` below is that aggregation, specified once and shared with the usage-share mechanism it was originally researched for.
- Bring-back candidates (opposing pass-catcher in a game-stack build), selected the same way from the opposing roster — **conditioned on the game environment actually supporting a full game-stack build (ADR-0021), not populated unconditionally.** `bring_back_candidates` is `None` when `game_stack_viability < 20.0` (on `GameEnvironmentScore`'s 0–100 scale), even when a confident opposing WR candidate exists — a real "this game/spread doesn't support a bring-back thesis" result, not a caveat appended to a still-populated list. This is now one of **three** distinct reasons `bring_back_candidates` can be non-populated, disambiguated by a new `bring_back_status` field (`"populated"` / `"no_confident_candidate"` / `"environment_unavailable"` / `"game_stack_not_viable"`) rather than collapsed into an ambiguous `None`:
  1. `"environment_unavailable"` (`None`, ADR-0017) — either team's `GameEnvironmentScore` isn't computable this week. No data to evaluate any thesis with.
  2. `"no_confident_candidate"` (`[]`, ADR-0019/`usage_share.py`) — both `GameEnvironmentScore`s are available and the game clears the viability floor, but no opposing WR clears the confident-candidate gate. Data is fine; no specific name can be confidently given.
  3. `"game_stack_not_viable"` (`None`, **new, ADR-0021**) — both `GameEnvironmentScore`s are available and a confident opposing WR may well exist, but `game_stack_viability` itself is below `20.0`: the environment doesn't support a full game-stack thesis at all this week, independent of whether a name is findable.

  `game_stack_viability` (below) keeps returning its real computed value in all three cases when computable — this gate governs only the candidate list and `pivot_to`'s bring-back clause (which is now only asserted when `bring_back_status` is `"populated"` or `"no_confident_candidate"`), not the diagnostic score itself. Full reasoning — including why the gate reads `game_stack_viability` itself rather than the spread dampener or the raw team-bottleneck alone, and why `20.0` — in ADR-0021 (`docs/adr/0021-bring-back-candidate-viability-gate.md`).
- **Single-team stack viability** = the team's own `GameEnvironmentScore` directly (0–100). No spread dampening — a lopsided spread doesn't undermine a plain QB + own-team-pass-catcher stack the way it undermines a bring-back.
- **Game-stack (bring-back) viability (ADR-0004, tail extended by ADR-0010)** = `min(GameEnvironmentScore(team_A), GameEnvironmentScore(team_B)) × spread_dampener(|spread|)`. Bottleneck logic — a stack is only as strong as the weaker team's environment, since a bring-back needs both halves of the game to produce, not just the stronger side. The spread dampener addresses Chris's game-script question and the Fantasy Football Expert's item 5 directly: a high combined `GameEnvironmentScore` with a lopsided spread doesn't support a real bring-back thesis, since the trailing team's passing volume in a blowout skews unreliable (checkdowns over the vertical/intermediate routes a bring-back is usually built on). Band edges, draft starting values pending Model Analytics Expert backtesting validation:

  | `\|spread\|` | Dampener |
  |---|---|
  | ≤ 3 | 1.00 |
  | 3–7 | 0.85 |
  | 7–10 | 0.65 |
  | 10–14 | 0.40 |
  | > 14 | 0.25 |

  The 10–14 / >14 split was added in ADR-0010 (Fantasy Football Expert re-review item 1) — the original single ">10 → 0.40" tail didn't distinguish a 10.5-point spread from a 24-point blowout; 0.25 (not zero) reflects that garbage-time bring-back production is unreliable, not impossible. This same band table is now reused by `DSTProjection`'s `own_team_script_multiplier` (ADR-0009) and Section 7's RB/DST penalty scaling (ADR-0010) — one table, three consumers. Spread comes from the Odds API — already pulled for `GameEnvironmentScore`'s implied-total component, no new data dependency. Full rationale and alternatives considered in ADR-0004 (`docs/adr/0004-spread-magnitude-dampening.md`) and ADR-0010 (`docs/adr/0010-review-round-2-refinements.md`).
- An explicit `pivot_to` field — the affirmative thesis for the stack, not just an absence of red flags. This mirrors the field added to the MLB `SlateStrategy` dataclass: a contrarian build needs a stated reason, not just constraint-based avoidance.

**`RoleShare` and `BlowoutVolumeDiscount` (ADR-0019) — player-level game-script usage-share signal.** Chris's own comparison of the walking-skeleton optimizer's output against his real submitted lineups surfaced a real gap: a pure vendor-blended projection is "following the field," and his own DET example (heavy positive-script rushing volume for Jahmyr Gibbs in two lineups, Amon-Ra St. Brown — a different vehicle for the same DET-game-environment thesis — in the third) is a claim that spread/expected margin should shift a *specific player's* expected share of his own team's carries or targets, sized by how concentrated that player's role already is. This is explicitly not a trench/coverage question (the existing `MatchupContext` rows) — it required new research, not a narrative judgment.

*Research, not assumption (full detail, all cited figures, and every rejected alternative in ADR-0019):* live-queried 2023–2025 nflverse play-by-play and schedules. The honest headline: a naive linear correlation between pre-game spread-derived margin and same-week usage share is close to zero (RB carry share: r=−0.008, n=1,486; WR1 target share: r=−0.026, n=1,540) — **taken at face value this does not support the original hypothesis.** Deeper analysis found a real but different mechanism: against *realized* game margin, a team's identified lead RB loses carry share in genuine blowouts (`|realized margin| > 14`) relative to close games — a statistically significant, magnitude-only effect (not direction — fires the same whether winning or losing big) of roughly 5–6 percentage points (Welch's t = 2.96–4.22, p<0.01) that shows up **similarly across bell-cow, mid-tier, and committee backs alike** — role concentration does *not* clearly gate the size of this specific effect, a genuine departure from Chris's original framing, stated explicitly rather than quietly dropped. The pre-game-actionable version of this signal is weaker still: NFL score margins vary widely around the closing spread, so a pre-game `|spread| > 14` (the trigger this formula can actually use at lineup lock) occurs in only 1.6% of games (2023–2025; 8.3% exceed 10) and only thinly supports the effect directly (n=5 at that exact cut). WR1 target share showed no usable signal, and what little exists ran opposite to a naive "trailing team dumps to its WR1" story (trailing-team mean target share 0.241 vs. leading-team 0.260) — consistent with, and independent confirmation of, `StackProfile`'s existing spread-dampener rationale (ADR-0004) that blowout garbage-time passing volume sprays across more targets rather than concentrating on the true WR1.

*Decision, given the weaker-than-hypothesized signal:* proceed with a hedged, damped version, not the full directional mechanism originally envisioned — recommended in ADR-0019 because (1) the underlying per-player role-concentration signal (`RoleShare`) has independent value regardless of this narrower finding, closing the `primary_stack_candidates` data gap above either way, and (2) even a small, rare-triggering, magnitude-only discount is a real GPP differentiator in exactly the double-digit-spread games where the field is likeliest to misprice the chalk starter.

```
RoleShare (per player, RB or WR, trailing season-to-date through last completed week):
  role_share_blended = w(n) * role_share_current_to_date + (1 - w(n)) * role_share_league_prior
  w(n) = n / (n + k),  n = weeks played through W-1,  k = 6  (reuses pace/PROE's k, ADR-0011 pattern)
  league_prior: RB lead-back share = 0.504, WR1 share = 0.236 (this ADR's own 2023-2025 computation)
  RB role tiers (empirically cut, not backtested): bell-cow >= 0.60, mid-tier 0.45-0.60, committee < 0.45

BlowoutVolumeDiscount (identified lead RB only -- any role tier; WR1 gets no formula, see below):
  |pregame_spread| <= 10       -> 1.00
  10 < |pregame_spread| <= 14  -> 0.97   (thin support -- interpolated, conservative)
  |pregame_spread| > 14        -> 0.93   (damped ~50% below the observed 8-13% realized-outcome decline)

  adjusted_carry_share = identified_lead_rb.role_share_blended * blowout_volume_discount(|pregame_spread|)
```

Applied at the same Section 5 step-4 pipeline point as `MatchupContext` — this shapes the RB's expected *volume* share, `MatchupContext`'s run-game row shapes *efficiency* on top of it; the two multiply together, not combined via the capped log-space method (that method exists to stop double-counting two grades of the *same* axis, and volume/efficiency are genuinely independent axes here). **No WR1 target-share tilt is specified** — an explicit hold, not a silent gap, so a future pass doesn't re-run this same research to rediscover a null result. Band edges/multipliers above are flagged, damped, low-confidence starting values pending Model Analytics Expert + Fantasy Football Expert sign-off and eventual `ProjectionAccuracyRecord` (ADR-0018) backtesting.

**Structural placement, an explicit call (full reasoning in ADR-0019):** this lives under `StackProfile`, not as an extension of `MatchupContext`'s "Scheme / game flow" row and not as a new `MatchupContext` row — it has no opposing unit in it at all (every real `MatchupContext` row is a unit-vs-unit grade differential), and "Scheme / game flow" is already a different granularity (team-level PROE/pace feeding `GameEnvironmentScore`, not a player-level multiplier). It answers `StackProfile`'s own question instead — "which player, within an already-scored game environment, is the right vehicle" is literally Chris's framing of his own DET example. **Scope flag for the Product Owner, not decided here:** this is a real, if modest, expansion of `StackProfile`'s job from "stacking/correlation candidates" to "primary-vehicle selection more generally" (a team's lead rusher isn't historically a stacking leg) — flagged per the Architect's decision-rights boundary rather than resolved unilaterally.

**Ingestion gap flagged for the Data Integration Engineer (ADR-0019):** `src/nfl_dfs/ingestion/nflverse.py` today only aggregates play-by-play to **team-week** grain (pace/PROE) — nothing in the ingestion layer touches `rusher_player_id`/`receiver_player_id` at all. A new module is needed to compute player-week carry/target shares against the existing team-week denominators, identify each team's lead RB/WR1 **trailing-only** (weeks `1..W-1`, not the full-season hindsight this ADR's own research used as a backtest simplification — a live pipeline cannot use future weeks to identify who "the lead RB" was), gated the same way ADR-0006/ADR-0012 gate defender/returner identification (draft starting gate: RB >40% trailing share and >=15 trailing carries, WR >18% trailing share and >=20 trailing targets, falling back to "no identified player this week" rather than a guess when the gate fails), then blended via the already-implemented `shrinkage_weight`/`blend_toward_prior` helpers against the two league-prior constants above. No new data source — same `import_pbp_data()` call already used for pace/PROE; pre-game spread is already ingested via `odds_api.py`.

### MatchupContext
Player projections built purely from historical performance miss the thing that matters most in football: what happens at the point of attack this week. `MatchupContext` is a unit-vs-unit adjustment layer, computed before the projection blend, not after — so it shapes the projection rather than just tagging it with a note. Every adjustment must trace to a specific stat or grade the pipeline pulls and computes against — never a narrative judgment applied at build time with no numeric input behind it. If the data doesn't support an adjustment, no adjustment is made.

**Status: run game and pass protection are data-confirmed as originally scoped (and richer than assumed — see below). Coverage is data-confirmed for the man/zone-scheme piece (with a documented shell-level blind spot, see below); the alignment (slot/perimeter) piece required an approximation — see ADR-0001 (`docs/adr/0001-matchup-context-alignment-coverage.md`), now with statistical confidence gates and a shadow-coverage guardrail (ADR-0006, `docs/adr/0006-alignment-coverage-confidence-gates.md`). Pass-protection and coverage multipliers now combine via a capped log-space method rather than naive multiplication (ADR-0005). Scheme/game flow is unchanged, just re-pointed at the correct nflverse function.**

**Grade population — trailing, season-to-date through the most recently completed week (ADR-0014, `docs/adr/0014-matchup-context-trailing-grade-population.md`).** PFF's grades are inherently trailing by construction — film-graded after plays happen, not a pre-game projection — confirmed directly by Chris after the Data Integration Engineer's live ingestion test found 0/210 matches against a pre-kickoff slate (there's no "this week's" grade for a game that hasn't been played). Every PFF-grade input below (Run game, Pass protection, Coverage man/zone) uses the same cutoff discipline already established for `GameEnvironmentScore`'s pace/PROE (ADR-0003): season-to-date cumulative through the last *completed* week, never the current week. Confirmed live against PFF's OpenAPI spec that the general facet endpoints these rows depend on accept the same comma-separated `week` list Phase 0 already found for the `signature` family (`week=1,2,...,W-1`), and — better than expected — PFF aggregates server-side across that list (one row per player, a `player_game_count` field, no per-week rows to merge client-side), so this is a single API call per endpoint, not a per-week pull-and-aggregate. No blending toward a prior-season baseline for weeks 2+ (unlike pace/PROE) — individual PFF grades need a player-identity-matched anchor, not a team-level one, which is a larger v1.1 scope addition; **week 1 specifically** (zero completed current-season weeks, cumulative is undefined rather than just noisy) falls back to that same player's own prior-season (2024/2025) PFF grade by `player_id`, or a league-average-by-position grade if no prior-season record exists (e.g., a rookie). Full reasoning, the live API confirmation, and Data Integration Engineer direction for `pff.py`'s next ingestion pass are in ADR-0014.

### DSTProjection
**Status: structure confirmed sound by both experts' fresh re-review (nothing re-architected); two narrow fixes closed this pass — a bonus-magnitude bug (data-derived correction) and a returner-population/gating/baseline spec gap. Both experts consider this the final fix round for `DSTProjection`; remaining items are backtest-queue entries, not open spec gaps. Current spec is ADR-0009 (structure, `docs/adr/0009-dst-projection-rework.md`) + ADR-0012 (return-opportunity signal, `docs/adr/0012-return-opportunity-signal.md`) + ADR-0011 (shared shrinkage form, `docs/adr/0011-shared-shrinkage-functional-form.md`). ADR-0008 remains superseded, historical-only.**

DST is a mandatory roster slot in every lineup (Section 3), and Section 3 already establishes it needs its own treatment — volatile, TD/sack-driven, not a scaled-down offensive model. `MatchupContext` above honors that by never folding DST into the offensive-skill-position rows; `DSTProjection` is the missing other half — DST's own scored basis.

Chris's direction on the first draft, verbatim: *"I think this is a good example of where scheme and script matters. For defenses, just giving up the least points isn't necessarily the best indication of DFS scoring. We need sacks, turnovers etc. Special teams TDs also come into play so you could have a mediocre D with a great returner that should pop."* And on the discrete-event problem specifically: *"These seem hard to predict. We want the opportunities."* — i.e., don't build a TD-probability model (that's Phase 4 simulation territory, Section 12/13), model opportunity-shaped proxies instead. This reshapes the formula into a tiered structure — sacks/turnovers as the dominant core, points-allowed-style context as a demoted secondary factor, and a new, additive return-opportunity signal so a strong returner can add value independent of the base defense's grade.

**Baseline** — unchanged: a blended vendor DST point projection (PFF/RotoGrinders/Footballguys DST-specific projections where published), combined the same way offensive player projections are blended in Section 5 step 3. A source without a DST-specific number is excluded from that team's blend rather than substituted with an offensive-model figure.

**Core — sack + turnover opportunity (dominant driver, wide range):**
- `sack_opportunity_multiplier` — this DST's own pass-rush grade/win rate vs. the opposing offensive line's pass-block grade (same matchup as the Pass protection row above, defense's-side view). 0.85x–1.15x cap.
- `turnover_opportunity_multiplier` — a blend of the opposing offense's INT/fumble rate (nflverse, **QB-continuity-adjusted**: when ingestion confirms a starter change via the same starter-status channel `GameEnvironmentScore`'s injury/role flag already uses, the input shrinkage-blends the new starter's own turnover rate toward the *league-average starting QB* rate — not an invented "backup penalty" — using the shared empirical-Bayes form (ADR-0011): `w = career_attempts / (career_attempts + 150)`) and this DST's own pressure rate as a turnover-*opportunity* proxy (pressure creates tipped-pass/strip-sack chances independent of whether it converted this week — the "opportunity, not outcome" framing Chris asked for). 0.85x–1.15x cap. **Known v1 limitation:** pressure rate alone doesn't distinguish blitz-generated pressure from coverage-sack (broken-play) pressure, which carry different takeaway profiles — documented here as a known gap, not resolved by man/zone or any other confirmed field this pass; havoc rate / tackles-for-loss are flagged as a v1.1 candidate addition if backtesting shows the undifferentiated pressure-rate proxy is too noisy.
- These combine via the ADR-0005 capped log-space method, **±20% combined cap** — deliberately, since both legs now intentionally share this DST's own pressure-rate data. **Sharpened backtest task:** decompose `turnover_opportunity_multiplier`'s variance into its pressure-driven component vs. its independent opposing-offense-turnover-rate component; if the independent piece is being drowned out by the shared pressure signal, down-weight the pressure sub-component specifically rather than just re-checking the outer cap.

**Context — demoted, narrow range (secondary, not co-equal):**
- `opponent_implied_total_multiplier` — opposing team's implied total, inverted (unchanged direction from the first draft), but **cap tightened to 0.90x–1.10x** (from 0.85–1.15) — the direct fix for "giving up the least points isn't necessarily the best indication": the signal stays, but can no longer swing the projection as far as sack/turnover opportunity.
- `own_team_script_multiplier` — **new**, closing the Fantasy Football Expert's own-team-script gap: this DST's own team's spread magnitude (either direction — a big favorite risks garbage-time bench rotation, a big underdog's opponent can run clock rather than keep passing once ahead, both plausibly reducing real opportunity). Banded on spread magnitude alone, reusing the same band edges as `StackProfile`'s spread dampener below (ADR-0010): ≤7 → 1.00, 7–10 → 0.97, 10–14 → 0.93, >14 → 0.90.
- Combine with the already-capped core via the same log-space method, **outer combined cap ±30%**. **Asymmetry, stated explicitly rather than implied symmetric:** the "demoted relative to core" framing holds cleanly for upside (context tier max ≈ +10%, from `opponent_implied_total_multiplier` alone, since `own_team_script_multiplier` never exceeds 1.00) but not for downside (context tier max ≈ −19%, from both legs bottoming out together — nearly as large as the core's own ±20% floor). Both experts should weigh whether this asymmetry needs correcting or is an acceptable reflection of "bad context signals stack, good ones don't compound the same way."

**Return-opportunity — new, additive, not folded into the multiplicative stack (population, gating, and baseline fixed in ADR-0012 after the second re-review; bonus scale corrected in the same pass):**
- Identified **separately per return role** (punt, kickoff) — not one blended "the returner." Real nflverse data (2024–2025) shows why: punt-return duty is concentrated (median primary-returner share of a team's punt-return attempts: 81.7%; a >50% majority-holder exists for 89% of team-seasons) but kickoff-return duty is not, under the post-2024 dynamic-kickoff rules (median primary-returner share: 44.1%; only 31% of team-seasons have a clear majority holder).
- **Identification gates per role (ADR-0012, reusing ADR-0006's pattern):** plurality returner must hold an absolute majority (>50%) of that role's live-return attempts, and clear a floor of **8 live-return attempts**, over a **season-to-date** identification window (not ADR-0006's 3-week window — return attempts are too rare for a 3-week sample to be meaningful; full-season medians run 15–20 attempts per role). If the gate fails for a role (the norm for kickoff, per the concentration data above), fall back to team-level return production for that role, unweighted by individual identity.
- `returner_volume_z` / `returner_explosiveness_z` — z-scored per role, per team, cross-sectional per week, from live-return attempts (excluding fair catches/touchbacks/blocked punts — confirmed distinguishable via nflverse's `punt_fair_catch`/`punt_downed`/`kickoff_fair_catch`/etc. flags) and `return_yards` grouped by `punt_returner_player_id`/`kickoff_returner_player_id`.
- **Prior-season baseline — identity-matched, not team-keyed (ADR-0012 bug fix):** the current-season-to-date blend only references a specific player's own prior-season rate when that same individual (matched by player ID) is confirmed as the team's primary returner for that role in the prior season too. Real data: that recurrence happens in only 31.2% of team-seasons for punt returners, 15.6% for kickoff — so in the large majority of cases the blend instead references a **league-average returner baseline**, not the team's own historical number, closing the rookie/newly-traded-returner cold-start gap. The prior baseline itself is partial-pooled toward the league-wide 2-season average before use (ADR-0011/ADR-0012 shared shrinkage form, `k=25`), and the current-season blend toward that pooled baseline uses `k=10` (both new entries in ADR-0011's shrinkage table) — both chosen from the same live attempt-count data, not guessed.
- **Data check (done live, not assumed):** downloaded and queried `nflverse-data`'s 2024/2025 play-by-play directly — returner identity, return yards, return-TD flag, and the fair-catch/touchback flags needed to isolate live-return attempts are all real, confirmed fields; same `import_pbp_data()` source already used for pace/PROE, no new data dependency, no fallback to DK/PFF/RotoGrinders/Footballguys needed. Caveat: the 2024 dynamic-kickoff rule change means kickoff-return-volume comparisons should stay within the 2024/2025 baseline window, not reach further back.
- `return_opportunity_multiplier` = capped log-space combination of `punt_return_opportunity` and `kickoff_return_opportunity` (each itself a capped log-space combination of that role's volume-z/explosiveness-z, 0.85x–1.15x per leg), equally weighted for v1 — weighting by each role's share of total return attempts is a flagged backtesting candidate, not decided here. Converted to a **points bonus, not a multiplier on the baseline**: `return_opportunity_bonus = (return_opportunity_multiplier − 1.0) × 4.5 DK points` (**corrected from an earlier 3.0 — see below**). Additive because a strong returner situation must be able to add value regardless of how the core defensive multiplier reads — Chris's "mediocre D with a great returner should pop" scenario fails under a multiplicative fourth leg, where a weak core would suppress it.
- **Bonus-scale bug and fix (ADR-0012):** the original 3.0-point anchor was applied *after* the ±20% cap, so the realized max bonus was only `0.20 × 3.0 = 0.6` points — not enough, by the numbers, for a mediocre-defense-elite-returner team to outscore an average team's projection, failing Chris's scenario on magnitude even though the structure was right. Fixed by computing the real figure from 2024–2025 nflverse data rather than guessing: team-weeks in the top decile of combined return volume/explosiveness z-score showed a **17.4%** rate of scoring ≥1 return TD that week, vs. **2.8%** league-wide average and **1.1%** outside the top decile — at 6 DK points per return TD, that's a marginal (top-decile-minus-average) value of **~0.9 points**. The scale constant was corrected to **4.5** so the max bonus (`0.20 × 4.5 = 0.90`) matches that computed marginal figure directly; **the existing ±20% cap did not need widening** — the bug was the scale constant, not the cap. Sample caveat: only 32 total return TDs across the 2-season window underlie this figure — an early, concrete Performance Analytics backtest candidate once live results exist, not a converged estimate.
- **Known remaining tension, not resolved this pass:** because the core defensive multiplier and the vendor baseline may both already reflect a team's known defensive quality, a "mediocre defense" case can be discounted twice (low baseline, then a sub-1.0 core multiplier) before the corrected +0.9-point bonus is added — which can still leave an extreme mediocre-D/elite-returner case short of an average team's total. Fixing this would mean touching the core/context tiering itself, which both experts confirmed should stay as-is this round — flagged for the backtesting queue, not fixed here.

```
core = capped_log_combine(sack_opportunity_multiplier, turnover_opportunity_multiplier, cap=±20%)
combined_defensive_multiplier = capped_log_combine(core, opponent_implied_total_multiplier, own_team_script_multiplier, cap=±30%)
return_opportunity_multiplier = capped_log_combine(punt_return_opportunity, kickoff_return_opportunity, cap=±20%)
return_opportunity_bonus = (return_opportunity_multiplier - 1.0) × 4.5
final_dst_projection = (baseline_dst_projection(team) × combined_defensive_multiplier) + return_opportunity_bonus(team)
```

Full derivation, the QB-continuity mechanism, and alternatives considered are in ADR-0009 (structure) and ADR-0012 (return-opportunity population/gating/baseline fix and bonus recalibration). **Flag for the Data Integration Engineer, not resolved here:** check whether PFF/RotoGrinders/Footballguys' vendor DST baseline projections already price in known returner history — if so, the additive return bonus is partially double-counted against the baseline and should be reframed as measuring marginal deviation from what vendors already price in, not the full signal (see Section 11).

### ProjectionAccuracyRecord
**Status: new construct (ADR-0018), draft spec, pending Model Analytics Expert confirmation on the attribution mechanism.** Closes the standing backtest-queue problem that every prior ADR in this section deferred ("flagged for Performance Analytics once live results exist") by specifying the thing that actually runs those checks, rather than leaving them as unexecutable notes.

Every ADR from 0003 onward set a threshold, cap, or weight to a stated starting value and logged a validation item against it once real results existed. `ProjectionAccuracyRecord` is the construct that makes those items runnable: a decomposed, per-player-week snapshot of everything that fed a projection (baseline vendor blend, every `MatchupContext` leg's individual multiplier and point contribution, every `GameEnvironmentScore` input, `DSTProjection`'s legs for DST), joined once the game is final against a real actual-result row, so a later query can isolate "how much did the coverage adjustment specifically move this projection" rather than only comparing one blended number to one final score.

**Two halves:** a `ProjectionSnapshot` (written pre-lock for a live week, or by a backtest run for a historical week — immutable, never overwritten by a re-run) and an `ActualResult` (written once the game is final, from real box-score data — never estimated). The parent record is the two joined on `(canonical_player_id, season, week)`, plus derived residual fields.

**Decomposition, not a single number.** Every Section 6 combination step already computes a sum of log-multipliers before capping (`capped_log_combine`, ADR-0005/0009/0012/0015's shared pattern) — the snapshot retains those individual log terms instead of discarding them after the final `exp()`, which makes exact per-leg point-contribution attribution a byproduct of the formula as already specified, not a new counterfactual re-run. It also records `cap_absorption` (how much a combination's cap actually suppressed that week) as its own queryable field, directly answering several ADRs' own "is this cap binding, and is it sized right" questions.

**Actuals source — checked live, not assumed (ADR-0018):** `nflverse-data`'s `stats_player` GitHub release tag (**distinct from `player_stats`**, the tag Phase 0 already found stale through only 2024) is live, weekly-grain, and current — its `stats_player_week_2026.csv` asset was last updated the same day as this session, with real Week 1 2026 rows already in it. The installed `nfl_data_py` package's `import_weekly_data()` convenience function does **not** read from this fresher tag (confirmed against the package source — it's hard-coded to the stale `player_stats` release), so actuals are computed by aggregating `import_pbp_data()` directly — the same source and pattern already used for pace/PROE — with the `stats_player` release used as an independent cross-check, not the primary path. `dk_actual_points` is computed from raw box-score stats by a single versioned function against DK's own published scoring rules, not read from any vendor.

**Retroactive backtesting without look-ahead bias — reuse-vs-generalize audit (full detail in ADR-0018 section 4):** ADR-0014's trailing-grade population (season-to-date through the last completed week) and ADR-0003's z-score population/cutoff/shrinkage design are **already point-in-time-correct by construction** — both were built "as of week W," not "as of now" — and are directly reusable for a historical week with zero new logic, just different `season`/`week` parameters. The two live-data-polling mechanisms built for a weekly-cadence problem (ADR-0016's Odds API cache, and the weather forecast endpoint) need a **different historical source, not new logic**, and both have a confirmed, live-checked, zero-new-dependency replacement: `nfl_data_py.import_schedules()` carries historical `spread_line`/`total_line` with confirmed 100% coverage across 2023–2025, and Open-Meteo's historical Archive API (`archive-api.open-meteo.com`, confirmed live) returns the identical wind/temperature/precipitation fields the forecast endpoint does, just for a past date. Two genuine, unresolved gaps, flagged rather than papered over: RotoGrinders' injury-severity grading has no confirmed historical archive (`nfl_data_py.import_injuries()` is a plausible but unverified substitute, and structurally cruder — no `IMPACTRTG`-equivalent severity), and vendor DFS-projection baselines (RotoGrinders/Footballguys, and PFF's *projection* facet specifically, as opposed to its confirmed-historical *grade* facets) have not been confirmed to support historical-week pulls at all — full projected-total-vs-actual-total backtesting is gated on that, though the large majority of queued component-level backtest items are not.

**The compiled backtest queue, reorganized by what this construct directly enables vs. what still needs new data ingestion or a Product Owner scope decision, is in ADR-0018** (`docs/adr/0018-projection-accuracy-record.md`) — 12 of 16 previously-unexecutable queue items (spanning `GameEnvironmentScore`, `MatchupContext`, and `DSTProjection`) become direct queries against stored snapshot + actual data; the remaining 4 need new data ingestion (run-game gap/zone split, shell-level coverage grading) or are scope/data-source questions this construct doesn't touch either way (coordinator-level scheme attribution, the dome-travel v1.1 candidate).

**Scope flag for the Product Owner, not decided here (see Section 11):** Section 10 gates "how the tool is performing" tracking to Performance Analytics, explicitly "can't run meaningfully until Phase 2–3 produce real output." Per-player projection-vs-actual tracking needs only projections (already Phase 1 scope) and real game results (already available) — not the optimizer or contest entries — so it isn't actually blocked by that gate. Whether building it now is simply unblocked Architect/Data-Integration-Engineer scope feeding Performance Analytics' eventual dashboard, or a phasing change to Section 10 that needs Chris's explicit sign-off first, is flagged for the Product Owner rather than decided unilaterally.

## 7. Lineup Construction Rules

- Every lineup must include at least one QB + pass-catcher stack from the same team.
- Game stacks (QB + pass-catcher + opposing skill player) are allowed and should be favored by `StackProfile.game_stack_viability` (Section 6), not by raw `GameEnvironmentScore` alone — that score already applies bottleneck (`min`) logic across both teams plus a spread-magnitude dampener on the bring-back thesis specifically (ADR-0004), so a lopsided spread suppresses game-stack favorability here even when both teams' individual `GameEnvironmentScore`s look strong. The dampening logic lives once, in Section 6/ADR-0004 — this rule consumes it rather than restating it, so the two don't drift out of sync if the dampener bands change.
- No more than one lineup in the generated set should share an identical core stack — the set needs to cover distinct theses, not variations on one favorite game.
- Because the same 3 lineups run in everything from a single-entry contest up to the Millionaire Maker, none of the 3 should be a pure small-field chalk build and none should be a pure max-leverage punt. The set as a whole should span that range — for example, one build closer to the strongest projected core, one or two built around a stated leverage thesis — so it performs reasonably whichever field size it lands in.
- RB/DST pairings that face each other are avoided by default but not hard-blocked; treat it as a scoring penalty, not a constraint — and per ADR-0004 (band-cliff fixed in ADR-0010), that penalty is **scaled by the RB's team's implied total and spread**, not flat, using a spread-magnitude *strength* term rather than a binary favorite/underdog sign check (a −0.5 vs. +0.5 spread is a coin flip either way and shouldn't land in categorically different buckets):

  ```
  strength(|spread| band): ≤3 → 0.0, 3–7 → 0.4, 7–10 → 0.7, 10–14 → 1.0, >14 → 1.2   (same band table as StackProfile's spread dampener, ADR-0010)

  penalty_multiplier(RB's team):
      underdog AND top-tertile implied total:     1.0 + 0.5 × strength(band)
      favorite AND bottom-tertile implied total:   1.0 − 0.5 × strength(band)
      otherwise (wrong tertile for the direction, or near-pick'em band ≤3): 1.0
  ```

  At the extremes this still lands near the original 1.5x/0.4x endpoints, but the near-pick'em cliff at zero spread is gone and the escalation across bands is graded rather than a single step. Reuses the same league-wide weekly implied-total tertile split computed for `GameEnvironmentScore` — no new data. Full rationale in ADR-0010 (`docs/adr/0010-review-round-2-refinements.md`).
- Salary usage floor: flag any lineup leaving more than a defined threshold of cap on the table unless it's an explicit punt build.
- Strategy count per slate is bounded — floor of 2, ceiling of 5 distinct builds, same bound used on the MLB side.

Not resolved here — needs a live check against actual vendor projection methodology/output (e.g., does a team's baseline projection move when its return specialist changes, holding defense constant), which only the Data Integration Engineer has the data access to check. If confirmed, the bonus should be reframed as marginal deviation from what vendors already price in, not the full signal — an Architect follow-up once this is answered, not resolved unilaterally now.
8. **Priority flag for the Data Integration Engineer — `weather.py` doesn't implement ADR-0015 yet.** Discovered during the `GameEnvironmentScore` implementation round: ADR-0015 (precipitation bands, the wind/temperature/precipitation three-way combination, the corrected wind-curve interior shape) was specified in a prior Architect round, but the corresponding `weather.py` ingestion update never happened — only the PRD/ADR text was written. `weather.py` today still only pulls Open-Meteo's combined `precipitation` field and a binary flag, not the `rain`/`snowfall` split or an hourly rate. `GameEnvironmentScore`'s computation currently — correctly, as a stopgap — treats a missing precipitation leg as neutral rather than guessing at a value, but this means the weather sub-component silently understates its true effect on every game with meaningful rain or snow until this is implemented. Nothing further to design here (see ADR-0015's handoff note) — this is a ready-to-implement task, next in line for the Data Integration Engineer's weather ingestion pass.
9. **Scope call for the Product Owner, not decided here — does `StackProfile`'s new `RoleShare`/`BlowoutVolumeDiscount` mechanism (Section 6, ADR-0019) expand `StackProfile`'s job description beyond stacking/correlation?** `StackProfile` is scoped in this PRD as "the correlation thesis for a given team/game" — QB + pass-catcher stacking candidates. ADR-0019's `RoleShare` signal also now covers a team's primary rusher, who isn't historically a stacking leg (an RB's carries don't correlate with the QB's passing yards the way a pass-catcher's targets do) — it's a broader "which player is the right vehicle for this game environment" question. The Architect placed it under `StackProfile` anyway (see ADR-0019's structural-placement section) because it answers the same underlying question and because `MatchupContext` is a worse fit (no opposing unit in the formula at all), but whether that's a natural extension of `StackProfile`'s existing scope or ought to be tracked as a distinct construct is a Product Owner call, flagged rather than resolved unilaterally.
10. **Scope call for the Product Owner, not decided here — does building `ProjectionAccuracyRecord` (Section 6, ADR-0018) now pull part of Performance Analytics' Phase 2–3-gated scope forward into Phase 1?** Section 10 gates "how the tool is performing" tracking to Performance Analytics, explicitly "can't run meaningfully until Phase 2–3 produce real output" (full lineup ROI, contest-level results). But `ProjectionAccuracyRecord`'s per-player projection-vs-actual tracking doesn't need the optimizer, generated lineups, or contest entries at all — only projections (already Phase 1 output) and real game results (already available, historically and as each live week completes), which makes it genuinely unblocked by the same gate Section 10 describes. Two live options, neither decided by the Architect: (1) treat this as ordinary Architect/Data Integration Engineer scope within Phase 1 that happens to also feed Performance Analytics' eventual dashboard once Phase 2–3 exist — no phasing change, since it was never actually blocked on the optimizer; or (2) treat building real accuracy-tracking infrastructure during Phase 1 as a phasing change to Section 10 regardless of technical unblocking, since Section 10's phase column reflects a scope decision Chris made, not just a dependency chain, and changing when a named role's work starts should get his explicit sign-off even when the technical dependency doesn't force it. See ADR-0018's Consequences section for the same flag in full.

## 12. Phased Roadmap

- **Phase 0 — Discovery:** Test connections to every source in Section 4 — auth, rate limits, and the actual fields returned. Confirm which specific PFF metrics referenced in Section 6 exist at the assumed granularity (pass-block efficiency by lineman, coverage grade by alignment, etc.). Capture and validate the RotoGrinders and Footballguys reverse-engineered endpoints via Claude in Chrome. Output is a data-availability report that Section 6's formulas get finalized against, owned by the Data Integration Engineer and reviewed by the Architect.
- **Phase 1 — Foundation:** Data ingestion for all sources, player ID reconciliation, and `GameEnvironmentScore` / `StackProfile` / `MatchupContext` finalized and implemented against Phase 0's findings.
- **Phase 2 — Optimizer wiring:** ILP lineup construction against the rules in Section 7, ownership/leverage layer, exposure reporting.
- **Phase 3 — Output & review tooling:** CSV export, lineup rationale generation, a lightweight review dashboard that includes Performance Analytics' hit-rate and ROI tracking once results start coming in.
- **Phase 4 (later, out of v1 scope):** Monte Carlo simulation layer, a multi-agent *runtime* pipeline (distinct from the subagent build/ops team in Section 10), Showdown/Captain Mode support.
